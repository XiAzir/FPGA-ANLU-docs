# 720p / 1080p，15fps 可行性核算

日期：2026-10-27。范围：C32源与既有报告、官方数据手册及显示时序的只读分析；未修改RTL/约束/位流，未构建、仿真或上板，高清素材尚未编码测量。数值采用十进制MB/s；器件64Mb存储容量为8MiB=8.388608MB。

## 判断与优先级

用户于本次分析后明确视频目标为1920×1080、15fps，后续方案按此目标收敛。需同时改造解码、帧缓存布局、内存服务与输出。720p15在下文保留为计算对照；此前先以720p15为下一档的建议已修正。已有SPI平均带宽余量描述当前640×480素材，高清方案需要逐环节预算。

## 1. HDMI输出路径

- C32 `IP/video_pll.v`：像素25MHz，串行125MHz；`lane_lvds_10_1.v`用5倍串行时钟和ODDR输出10bit编码字。
- C32 `final_area.txt`：HDMI四路均为`LVDS33_E`，引脚B10/C9、D11/D12、C11/A11、F10/H11。DS301物理第19页为BANK0的BE系列引脚。
- 官方DS300 v3.9.6物理第52页（印刷46页）2.7.2给出True LVDS最大400MHz/800Mbps，Emulated LVDS最大166MHz；物理第87页（印刷81页）高速I/O表同时列出相关标准。当前模拟差分路径需按对应模式、引脚和板级网络核准，高清输出不得直接套用True LVDS能力。
- Linux DRM CTA模式表已在线核对：720p60像素74.25MHz、1080p30像素74.25MHz、1080p60像素148.5MHz。按现有10bit/像素与5倍DDR串行器，串行时钟分别371.25/371.25/742.5MHz，每数据通道742.5/742.5/1485Mbps。
- 方案：先独立验证目标标准时序彩条；板载既有模拟差分路径的手册额定频率存在门槛，可评估改接合适的真差分I/O及匹配网络，或外接并行输入HDMI发射器。1080p内容15fps可选择1080p30扫描，每内容帧重复两次。低刷新自定义时序需结合显示器EDID/实际兼容性评估。

官方源码：[Linux drm_edid.c CTA模式表](https://kernel.googlesource.com/pub/scm/linux/kernel/git/torvalds/linux/+/refs/heads/master/drivers/gpu/drm/drm_edid.c)。查询摘录与源blob记录位于工程`development/hd_feasibility_20261027/display_mode_evidence.json`。

## 2. 共享IDCT的固定吞吐下界

当前JPEG核心与SD域同为50MHz。`jpeg/jpeg_idct.v`仅有一个共享算术核心，X/Y两趟各64个有效拍；4:2:0每16×16 MCU为6个8×8块，至少768拍/MCU。缓冲器、控制切换、流水等待、熵解码、SD读取及SDRAM背压另有开销。源码中未发现DC-only/零块直接跳过两趟IDCT的路径。

| 尺寸 | MCU/帧 | 50MHz IDCT理想最短时间 | 孤立IDCT理想帧率上限 |
| --- | ---: | ---: | ---: |
| 640×480 | 1200 | 18.432ms | 54.25fps |
| 1280×720 | 3600 | 55.296ms | 18.08fps |
| 1920×1080，按1088行MCU补齐 | 8160 | 125.3376ms | 7.98fps |

15fps预算66.6667ms/帧。720p IDCT本身已消耗约83%的完整内容周期；沿用当前等待显示完成后回收双缓冲的策略，还会压缩实际可用处理窗口。1080p15仅IDCT就要求至少94.0032MHz理想计算时钟，实际需更多裕量。降低JPEG质量能减轻读取/熵解码负荷，固定的128拍/块仍保留。

方向：拆分JPEG与SD时钟并评估75～100MHz候选，恢复两趟IDCT独立流水或采用更高吞吐算法，增加流水级缩短关键路径，重排帧提交/缓冲回收。C32 Slice8778/9800、DSP26/29、ERAM9K62/64（另有ERAM32K独立报告项），复制整套解码器的资源压力很大。以上均为方案，尚未实现。

独立只读子代理gpt-6-luna复核了128拍下界与无数值旁路；根代理已查看共享核心及几何实现。关键源码`jpeg_idct.v:32`、`:46`、`:64`、`:76`；同目录`jpeg_idct_ram.v`、`jpeg_idct_transpose.v`及`jpeg_idct_y.v`。

## 3. SDRAM容量、带宽和布局

官方DS301 v2.7.8物理第6～7页说明器件内置2M×32bit/8MiB SDRAM，规格最高200MHz、峰值800MB/s。C32实际配置50MHz×32bit，原始峰值200MB/s；控制器服务效率、刷新、读写切换与短突发均需另外计入。器件最高指标与当前控制器可达到的工作频率分别核验。

按视频RGB565，两像素/32bit字；内容15fps：

| 输出扫描 | 双帧有效存储 | 扫描读+解码写的平均数据量 |
| --- | ---: | ---: |
| 720p60 | 3.6864MB | 138.240MB/s |
| 1080p30 | 8.2944MB | 186.624MB/s |
| 1080p60 | 8.2944MB | 311.040MB/s |

这些数字只含有效像素，一次新帧写入加每扫描周期重新读出；当前640×480实际扫描约59.5238Hz。视频15fps与显示扫描频率分开预算。1080p60超过当前50MHz内存原始峰值；1080p30已经逼近该峰值，需提高效率/时钟或降低存储数据量。

1080p双RGB565有效帧仅余94,208B；若整帧按1088行存储，两帧8,355,840B，余32,768B。当前`frame_buffer_rgb888.v`为兼容RGB888图片按3byte/像素间距分配两槽，1080p两槽为12.4416MB，现有布局及几何检查需改。720p两槽5.5296MB可容纳。1080p还需处理1088行MCU写回与1080行可见区的差异。

方向：将内存控制器评估到75/100MHz，改善长突发/行局部性与仲裁；或保留JPEG本来的YUV420帧缓存，显示端再转换RGB。YUV420平均1.5B/像素，1080p双帧6.2208MB、1080p30读写139.968MB/s；代价是平面地址、色度复用、显示域颜色转换与行缓存改造。该方向解决容量及内存流量，TF压缩码率与IDCT计算另行预算。

## 4. TF读取及几何硬编码

- 当前SPI12.5MHz，原始1.5625MB/s；历史扇区服务模型1.353638MB/s。原声96kB/s持续占用，另需封装/FAT/等待与峰值余量。720p可先按视频6～8Mbps做离线素材候选与画质/峰值统计，再确定是否提速；高清实际码率尚未编码测量。
- 当前JPEG Q90视频有640×360有效内容、上下黑边；原片为1280×720，1080p素材实验会涉及放大。码率应对高清满画面重新编码统计，未将现有3.3165Mbps按像素倍数写成高清实测值。
- SPI分频0已是现实现最小值。25MHz候选需重做分频/采样或时钟域，并补输入输出时序；4位原生SD路线需先核对TF座DAT1/DAT2等与FPGA的实际连通。
- 顶层、JPEG固定宽高、`video_rgb_to_axis_640x480.v`行末、OSD/wipe坐标均需适配。`jpeg420_word_address.v`当前硬编码40个MCU列、9位像素行及640宽地址优化，720p/1080p必须同步重做。10:04回查修正：`mjp_file_reader.v`当前读取全局帧数及逐帧索引/长度，未读取并校验宽高；原先“头几何校验”的表述已删除，固定几何的证据在顶层JPEG参数、地址模块和显示模块。

## 10:04 按实际数据通路重梳1080p15

目标固定640×480/15fps升级1920×1080/15fps，像素处理量4.608增至31.104Mpixel/s，为6.75倍；按已有候选1080p30扫描，每内容帧显示两次。内容帧周期66.667ms，实际解码处理窗口还受缓冲交接影响。

1. **TF压缩文件读取**：当前媒体文件平均0.5221MB/s、SPI12.5MHz；高清素材实际码率尚未编码。先测1080p素材平均、最大帧和短窗口字节量，再选择质量/码率。SPI25MHz需改实现与板级时序；多扇区读取、扇区双缓冲及压缩数据预取可减少握手等待，并与解码重叠。降低码率主要减轻传输和熵解码负荷。
2. **熵解码与IDCT**：共享IDCT理想下界在50MHz为125.3376ms/帧；100MHz仍需62.6688ms，已接近完整66.667ms预算，需继续评估更高吞吐算法/流水/频率，结合实际处理窗口选定方案。新增DC-only或零AC块快速路径可作为算法候选，必须与当前数值结果对齐；当前无此旁路。提高JPEG质量压缩程度尚未改变当前固定IDCT拍数。
3. **几何与写回顺序**：640宽、40个MCU列及行位宽需改到目标几何；1080高涉及1088行MCU补齐与可见区裁切。`SD/frame_fifo_write.v`的JPEG路径`active_burst_size=4`，直接块序写回产生大量BL4短突发；评估块/行重排缓存，组合更长连续写操作，改善SDRAM实际效率。新增行缓存需纳入资源预算。
4. **帧缓存容量**：8MiB物理容量；现布局按RGB888两槽在1080p需12.4416MB，需修改。紧凑RGB565双帧8.2944MB，按1088行则8.35584MB；YUV420双帧可降至6.2208MB（有效1080行）。优先评估原生YUV420存储、显示端转RGB，按模式分配实际格式布局。
5. **SDRAM与双缓冲调度**：RGB565下1080p30读124.416MB/s、15fps写62.208MB/s，合计186.624MB/s；当前50MHz原始200MB/s。YUV420在每次扫描对色度做行缓存复用、每色度样本读取一次的条件下，读写139.968MB/s。结合75/100MHz候选提频、长突发、读写仲裁及实际返回所有权交接核算。保持C32实际返回排空语义；传输/解码/写入尽量流水重叠，帧提交遵守缓冲所有权，按可用窗口评价最慢帧。
6. **HDMI扫描输出**：目标1080p30为像素74.25MHz/现结构串行371.25MHz/数据通道742.5Mbps；现位流LVDS33_E模拟差分/串行125MHz，DS300对应模拟差分额定频率存在门槛。先确定引脚/板级匹配/输出实现能满足规格的路径，评估真差分改接或并行HDMI发射器，再运行独立彩条验证。
7. **原声与音画同步**：48kHz PCM16 mono仍96kB/s，15fps每帧3200个源样本。`wav_pcm_bridge.v`的PIXEL_HZ、测试音阶与OSD等现有25MHz时间基准应适配新的显示时钟。名义74.25MHz TMDS像素时钟配48kHz可用ACR N6144/CTS74250；需同步调整发生器并保持采样消费、暂停、重播和帧提交关系。声音吞吐压力基本保持，时钟参数属于必要适配。
8. **整体资源**：C32 Slice89.57%、DSP26/29，优化单核吞吐、搬移颜色转换与缓存组织优先做量化预算。频率候选与算法旁路均未实现；大规模复制核需要重新核算资源和时序。

推荐评估组合：1080p15 JPEG420 + 1080p30扫描 + YUV420双帧缓存/显示端颜色转换 + 块行重排长突发 + 更高吞吐IDCT + 按素材统计决定TF提速。验证顺序为输出路径、完整素材码率与离线帧周期、实际内存服务及交接、整机声画；本次仅整理方案。

计算产物：工程`development/hd_feasibility_20261027/budgets.json`；手册摘录在同目录`DS300*_selected.json`、`DS301*_selected.json`。本轮保留C32及修改暂停状态。

## 16:52追加：原生1080p30内容帧的瓶颈讨论

用户询问：如果P4可输出1080p30扫描，是否可让每次扫描显示一张新内容帧。以下为可行性计算，未修改15fps主线实现、未重编码30fps素材、未运行新TD/仿真/硬件测试。P4完整输出链仍待转接实测，C39当前现场证据为PLL锁定与帧计数活动。

### 输出端与内容帧

在P4实际1080p30输出成立的前提下，输出端可承载每秒30张不同画面。15fps每帧重复两次与30fps每次扫描一张新帧均为30Hz扫描，名义像素74.25MHz、DDR串行371.25MHz、每data lane742.5Mbps；变化集中在读取文件、解码、帧写入和调度。原声48kHz PCM16 mono仍96kB/s，双帧容量仍6,266,880B（含1088行存储补齐）。

### 算法与资源方向

- 当前native接口每拍最多输出一个样本，每帧3,133,440个Y/U/V样本；单这一项在100MHz的理想下界为31.3344ms，留给其余开销的空间很少。仅减小JPEG文件字节量时，完整尺寸样本输出仍在。
- 已有DC-only快速路径已经计入40.10755ms结果。后续可评估DC块直接产生打包32位写入字、减少64拍逐样本搬运，以及IDCT/块交接流水线；这是待实现/消融的算法方向。先前7代表帧的79.39% DC-only比例支持调查，收益尚未测量。
- JPEG域提频、mem/decode同域提频或新增跨域方案需配合时序/资源评估。C32正常播放器基线Slice89.57%、DSP26/29，C34完整高清资源尚未综合；复制完整第二解码核需要重新预算。
- 调度从每内容帧3200音频样本改为1600；20秒素材需保留原片30fps的600帧，并核对播放/暂停/重播与帧交换。原素材为720p30，1080尺寸依旧由放大得到，内容帧增加时保留来源说明。
